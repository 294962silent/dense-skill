# 实验设计

## 问题

压缩输出 token 的 skill 很多，但没人回答：**在保证任务完成度的前提下，哪个真的省？省的是哪一部分？**

## 三个可检验假设

- **H1（注入成本）**：技能文本越长，每次调用的输入成本越高；短技能在总成本上占优。
- **H2（内容增量）**：只加「不要写用户没要的东西」这类减法规则的技能，能在不丢必需信息的前提下显著减少可见输出。
- **H3（推理税）**：在推理模型上，输出压缩的大部分效果来自隐藏的 reasoning token 变化，而不是用户可见文本。

## 臂（arms）

统一基线是 `Answer concisely.`（4 token），每个 skill 臂 = 该基线 + SKILL.md 正文。这样测到的是**技能本身的增量**，而不是「简洁」这件事的普遍效果——caveman 仓库的 `evals/README.md` 把这一点写得很清楚，早期的评测因为和「无系统提示」比而虚高。

| 臂 | 来源 | 注入（实测） |
|---|---|---:|
| terse | `Answer concisely.` | 4 |
| micro | caveman-micro 6 行 | 90 |
| caveman | JuliusBrussee/caveman | 1112 |
| introvert | DeepakGanapathi97/introvert | 1686 |
| dense_v1 / v2 / v3 | 本文设计 | 342 / 221 / ~200 |
| dense_min / min2 | 极简版 | 104 / ~110 |

## 任务集

16 题，覆盖 8 类：决策（EN/ZH）、代码修复、诊断、抽取、数值、有序步骤、安全、解释、枚举。其中 **T13–T16 是留出题**，只在最后一轮跑，用来检查是否对前 12 题过拟合。

## 指标

1. **billed output** = `usage.completion_tokens`（含隐藏 reasoning，是真正计费的部分）。
2. **visible output** = 回复正文字符数 / 4（用户真正读到的部分）。
3. **pass** = 该题所有 `must_include` 正则命中 且 无客套/自述正则命中 且 不超过字数上限。这是二值，口径固定，不因臂而调整。
4. **facts** = `must_include` 命中比例（连续值，看压过头到什么程度）。
5. **total** = 输入 + 计费输出，衡量一次调用的真实成本。

## 统计

- 每个 (臂 × 题 × 重复) 一次调用；temperature 0.3，max_tokens 1024。
- 重复 5–8 次，取每题均值后再做臂间配对，避免把同一题的相关样本当成独立样本。
- 配对差值对 16 题做 bootstrap（2000 次）给 95% 区间；**报告区间而不是单点**。
- 判定标准：一个臂要算「更好」，必须在 total 或 billed 上给出显著下降，同时 pass 的下降不超过 5pp（本文预设的容忍度）。

## 已知局限

- 单一模型（deepseek-v4.1-flash）、单一温度，跨模型不可外推。
- 正则只能验证「必需事实在不在」，验证不了「理由对不对、语气合不合适」。pass 率是下界，不是质量分。
- 16 题 × 8 次仍然是小样本；pass 的 ±5pp 级差异不可靠，token 差异相对稳。
- 判分正则由作者编写，存在偏向自己设计的风险；留出题和预注册检查项只能部分缓解。
